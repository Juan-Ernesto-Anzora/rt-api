# Sprint 3 API ExecPlan - Admin and Configuration APIs

## Purpose

Sprint 3 adds tenant-scoped admin APIs for configuration data that currently must be managed through seed scripts, SQL, or Django admin. After this work, authorized tenant admins can inspect their effective permissions, review audit activity, and eventually manage workflows, statuses, transitions, users, memberships, roles, and permissions through API endpoints that the web admin UI can consume.

Day 1-2 focuses on the admin foundation and RBAC guardrails. A user with admin permissions can call `GET /api/admin/me/permissions/` to see who they are in the active tenant and which permissions they have, and can call `GET /api/admin/audit/` to review tenant-scoped audit events. Users without the required admin permission receive clean JSON `403` responses. Cross-tenant data must never leak.

There is no checked-in static `openapi-rt-with-examples.yaml` in this repo. OpenAPI is generated through drf-spectacular at `GET /api/schema`.

## Current Behavior

Current API behavior before Sprint 3:

- Authenticated requests use JWT and `X-Tenant`.
- Tenant-scoped request, lookup, dashboard, search, upload, transition, and notification APIs exist.
- `Role`, `Permission`, and `Membership` unmanaged models exist.
- `MembershipRole` and `RolePermission` are present only as commented-out model sketches in `apps/rt/models.py`, so the API currently cannot traverse role assignment or permission assignment through first-class Django models.
- No `/api/admin/...` endpoints exist.
- No reusable admin permission guard exists.
- `Activity` is tenant-scoped and can act as the first audit source, but there is no admin audit endpoint.

## Desired Behavior

Day 1-2 desired behavior:

- All admin endpoints require JWT and `X-Tenant`.
- Add an admin permission service or helper that resolves the current Django auth user to the tenant `dbo.User` record safely.
- Permission resolution must be tenant-scoped through `Membership`.
- Effective permissions should be returned with clean public fields and no internal Django names.
- `GET /api/admin/me/permissions/` returns the current user identity, tenant, roles, permissions, and admin booleans derived from effective permissions.
- `GET /api/admin/audit/` returns tenant-scoped `Activity` rows only when the caller has the required admin audit permission.
- Admin failures return clean JSON errors with `code`, `message`, and `details[]`; no stack traces or SQL errors.
- OpenAPI generated by drf-spectacular includes the new admin endpoints and request/response shapes.
- Negative tests prove unauthenticated, missing tenant, no membership, missing permission, and cross-tenant audit cases are blocked.

Permission names for Day 1-2 should be intentionally small and documented in code/tests. Seed-compatible names:

- `admin.read`: minimum permission to enter the admin area and call `GET /api/admin/me/permissions/`.
- `admin.audit.read`: permission required for `GET /api/admin/audit/`.

If existing seed data already uses different permission codes, record that in `Surprises & Discoveries` and adapt tests/implementation to the actual codes without broadening access.

Step 1: Confirm role/permission schema.

- Inspect `apps/rt/models.py` and SQL Server schema assumptions.

- If using Django models, add unmanaged models with explicit fields that match the existing SQL tables and record the decision here.
- If SQL joins are safer for composite-key tables, keep model changes minimal and isolate SQL in a small helper.

Step 2: Add admin permission resolution.

- Add a focused helper such as `get_admin_context(request)` or an `AdminPermissionService`.
- Resolve tenant from `request.tenant_id`.
- Resolve current tenant user by matching authenticated Django user to `User.email` where possible.
- Confirm user membership with `Membership.objects.filter(userid_id=<user_id>, tenantid_id=<tenant_id>).exists()`.
- Resolve effective roles and permissions only for the active tenant.
- Return a structured context containing tenant id, user id, display name, email, role names, permission codes, and helper booleans.
- If the auth-user to `dbo.User` mapping is ambiguous, fail closed with a clean `403` and record the limitation in `Surprises & Discoveries`.

Step 3: Add admin permission guard.

- Implement a small DRF permission/helper for required admin permission checks.
- Use it for admin endpoints rather than relying on frontend flags.
- Missing auth should remain `401` through DRF/JWT.
- Missing tenant should return `400 tenant_required` or existing tenant middleware behavior.
- Authenticated users without tenant membership or permission should receive `403 permission_denied` with JSON shape:

```json
{
  "code": "permission_denied",
  "message": "You do not have permission to access this admin resource.",
  "details": []
}
```

Step 4: Add `GET /api/admin/me/permissions/`.

Response shape:

```json
{
  "tenant_id": "00000000-0000-0000-0000-000000000000",
  "user": {
    "user_id": "00000000-0000-0000-0000-000000000000",
    "display_name": "Admin User",
    "email": "admin@example.com"
  },
  "roles": ["Tenant Admin"],
  "permissions": ["admin.read", "admin.audit.read"],
  "is_admin": true,
  "can_read_audit": true
}
```

- Require at least `admin.read`.
- Return sorted, deduplicated roles and permissions.
- Do not expose internal fields such as `userid`, `tenantid`, `roleid`, or `membershipid`.

Step 5: Add `GET /api/admin/audit/`.

Endpoint behavior:

- Require `admin.audit.read`.
- Query `Activity.objects.filter(tenantid=request.tenant_id)`.
- Default sort: newest first by `createdat`.
- Support pagination through DRF defaults.
- Optional safe filters can include `type`, `request_id`, `actor_id`, `created_from`, and `created_to` if implementation remains small.
- Response fields should be public names:
  - `activity_id`
  - `request_id`
  - `actor_id`
  - `type`
  - `payload`
  - `created_at`
- Cross-tenant activities must not appear.

Step 6: Add OpenAPI annotations.

- Use drf-spectacular serializers and `extend_schema` so `GET /api/schema` includes:
  - `/api/admin/me/permissions/`
  - `/api/admin/audit/`
- Include response serializers and error examples where local patterns support it.
- Because there is no static OpenAPI source file, generated schema is the contract for this repo.

Step 7: Add tests.

Positive tests:

- Admin permission context resolves a tenant member with `admin.read`.
- `GET /api/admin/me/permissions/` returns public user/role/permission fields.
- `GET /api/admin/audit/` returns only active-tenant activities.
- Generated OpenAPI includes admin permission and audit paths.

Negative tests:

- Unauthenticated requests are rejected.
- Missing `X-Tenant` is rejected cleanly.
- Authenticated user not mapped to `dbo.User` is denied.
- User not a member of active tenant is denied.
- Tenant member without `admin.read` cannot call `me/permissions`.
- Tenant member without `admin.audit.read` cannot call `audit`.
- Audit endpoint never returns activities from another tenant.

Add tenant-scoped workflow administration endpoints guarded by the baseline
`admin.read` admin permission:

- `GET /api/admin/workflows/`

- `PATCH /api/admin/workflows/{flow_id}/transitions/{transition_id}/`

Acceptance criteria:

- Workflow list/detail/create/update responses use public fields such as
  `flow_id`, `created_at`, `status_id`, `transition_id`, `from_status_id`,
  `to_status_id`, `guard_roles_json`, `guard_perms_json`, and `auto_rules`.
- All reads and writes are scoped to `request.tenant_id`.
- Status writes require the parent flow to belong to the active tenant.
- Transition writes require the parent flow to belong to the active tenant and

  explicit soft-delete or active flag for workflows, statuses, and transitions.

#### Confirmed schema model

Repository DDL and unmanaged models establish:

- `dbo.User` is a global RT domain identity keyed by `UserId`; email is globally
  unique and there are no password or Django authentication fields.
- `dbo.Tenant` is keyed by `TenantId` and has unique `Code`.
- `dbo.Membership` joins a domain user to a tenant and enforces unique
  `(TenantId, UserId)`.
- `dbo.Role` belongs to one tenant and enforces unique `(TenantId, Name)`.
- `dbo.MembershipRole` has composite primary key `(MembershipId, RoleId)`.
- `dbo.Permission` is a global catalogue keyed by `Code`.
- `dbo.RolePermission` has composite primary key `(RoleId, PermissionCode)`.
- `dbo.Activity` supports tenant-level admin events because `RequestId` is
  nullable in the current model and Sprint 3 upgrade SQL.

#### Public API contract

All endpoints require JWT and `X-Tenant`. Authorization requires baseline
`admin.read` and the endpoint-specific permission. Lists use `page`,
`page_size`, safe `sort`, and relevant filters such as `search`, `is_active`,
and `role_id`.

Users and memberships (`admin.users`):

- `GET /api/admin/users/`
- `POST /api/admin/users/`
- `GET /api/admin/users/{user_id}/`
- `PATCH /api/admin/users/{user_id}/`
- `GET /api/admin/memberships/`
- `POST /api/admin/memberships/`
- `GET /api/admin/memberships/{membership_id}/`
- `PATCH /api/admin/memberships/{membership_id}/`
- `DELETE /api/admin/memberships/{membership_id}/`. The approved hard-delete
  is transactional and guarded against dependency/default-tenant problems,
  final-admin removal, and actor self-lockout because the current schema has no
  membership soft-delete column.

Roles and membership-role assignments (`admin.roles`):

- `GET /api/admin/roles/`
- `POST /api/admin/roles/`
- `GET /api/admin/roles/{role_id}/`
- `PATCH /api/admin/roles/{role_id}/`
- `POST /api/admin/memberships/{membership_id}/roles/`
- `DELETE /api/admin/memberships/{membership_id}/roles/{role_id}/`

Permission catalogue and role-permission assignments (`admin.permissions`):

- `GET /api/admin/permissions/`
- `POST /api/admin/roles/{role_id}/permissions/`
- `DELETE /api/admin/roles/{role_id}/permissions/{permission_code}/`

No permission-catalogue mutation endpoint is included. Permission codes remain
deployment-controlled because changing them affects server authorization.

Public response fields:

- User: `user_id`, `email`, `display_name`, `employee_code`, `avatar_url`,
  `is_active`, `created_at`, `updated_at`.
- Membership: `membership_id`, `user`, `is_default_tenant`, `roles`,
  `created_at`; never expose `tenantid_id` or `userid_id`.
- Role: `role_id`, `name`, `description`, `permissions`, `created_at`.
- Permission: `code`, `description`.

Write payloads and semantics:

- Create user: `email`, `display_name`, optional `employee_code`, `avatar_url`,
  and `is_default_tenant`. Atomically create `dbo.User` and its active-tenant
  `Membership` so a tenant-scoped user never becomes invisible.
- Update user: public profile fields and `is_active`; deactivation replaces hard
  delete because users may have dependencies.
- Create membership: `user_id`, optional `is_default_tenant`.
- Update membership: `is_default_tenant` only. Setting true atomically clears
  other defaults for that domain user; reject clearing the only default unless
  another default is selected in the same transaction.
- Create/update role: `name`, optional `description`. Protect canonical role
  names from rename; expose no role delete without soft-delete support.
- Assign role: `{ "role_id": "<uuid>" }`.
- Assign permission: `{ "permission_code": "admin.users" }`.

#### Domain-user and tenant safety rules

- `dbo.User` is the RT domain user. User creation must not create a Django
  `auth_user`, password, JWT credential, or OIDC account.
- A domain user becomes login-capable only when the existing authentication
  provisioning path creates/maps a Django identity with the same verified email,
  or later through OIDC. Day 5-6 documents this but does not invent passwords.
- User list/detail/update scopes through active-tenant `Membership`, because
  `dbo.User` has no `TenantId`.
- A user may be shared across tenants. Return `409 shared_user_conflict` for
  profile/deactivation PATCH when memberships exist outside the active tenant;
  broader global identity administration is deferred.
- New memberships and role assignments require `User.IsActive = 1`.
- Cross-tenant IDs return tenant-scoped `404`; authenticated callers lacking a
  required permission receive `403`.
- Invalid path UUIDs return clean `404`; invalid body UUIDs return clean
  `400 validation_error` responses; neither may return 500.
- Duplicate email, membership, tenant role name, membership-role, and
  role-permission operations return clean `409 conflict` or field-level `400`
  without SQL text. Duplicate assignments use `409`, not a fake success/audit.

#### Final-admin and self-lockout protection

Potential lockout operations run in `transaction.atomic()` and lock relevant
tenant memberships, role links, and role-permission links before rechecking:

- Every tenant retains at least one active membership whose roles include
  canonical `RT Admin` and whose effective permissions include `admin.read`.
- Block deactivating that user, deleting that membership, removing its final
  `RT Admin` assignment, renaming the canonical role, or removing permissions
  when the result would leave no active tenant admin.
- Independently block the actor from deleting/deactivating their own membership
  or removing their own final effective admin role, even if another admin exists.
  Return `409 admin_lockout` with a clear message.
- Checks are permission-aware and name-aware so a malformed `RT Admin` role
  without `admin.read` is not counted as valid coverage.

#### Audit behavior

Every successful write creates one tenant-level `Activity` in the same
transaction with `requestid_id=None`, the RT domain actor, public IDs/changed
fields in JSON payload, and one of these types:

```text
admin.user.created
admin.user.updated
admin.user.deactivated
admin.membership.created
admin.membership.updated
admin.membership.removed
admin.membership.role_assigned
admin.membership.role_removed
admin.role.created
admin.role.updated
admin.role.permission_assigned
admin.role.permission_removed
```

Rejected, duplicate, and no-op requests create no audit row. Never create a
fake request solely for auditing.

- 2026-06-10: `Role`, `Permission`, and `Membership` models exist as unmanaged SQL Server models.
- 2026-06-10: `MembershipRole` and `RolePermission` are currently commented out in `apps/rt/models.py`, so Day 1-2 must explicitly decide whether to add unmanaged models or isolate raw SQL joins.
- 2026-06-10: No `/api/admin/...` routes exist yet in `rt_api/urls.py`.
- 2026-06-10: No static OpenAPI source file is checked in; the API contract is currently generated by drf-spectacular at `/api/schema`.
- 2026-06-10: Django 5.2.5 is installed, so unmanaged `MembershipRole` and `RolePermission` can use `models.CompositePrimaryKey` instead of raw SQL for the join tables.
- 2026-06-10: Existing tests favor manager monkeypatches and generated schema checks, so admin guardrail tests can cover RBAC behavior without depending on a live SQL Server.
- 2026-06-12: Postman/manual validation showed the database seed and effective RT Admin permissions use `admin.read`; `admin.access` was not seeded and caused valid admins to receive `403`.
- 2026-06-12: `Flow`, `Status`, and `Transition` do not currently have
  `IsActive`, `ArchivedAt`, or `UpdatedAt` columns, so Day 3-4 should avoid
  delete/archive endpoints instead of pretending hard deletes are safe.
- 2026-06-12: `Activity.RequestId` was modeled and scripted as required, but
  admin configuration audit events are tenant-level and not tied to a request.
  The Day 3-4 audit implementation requires nullable `RequestId` for those
  events while preserving request-linked activity behavior.
- 2026-07-29: Live ACME verification confirmed `admin@example.com` has the
  `RT Admin` role plus `admin.read` and `admin.workflows`; the current API
  returns `200` from `/api/admin/me/permissions/` and
  `/api/admin/workflows/` for that identity.
- 2026-07-29: The web route guard redirects before calling the admin API
  because it derives admin access only from JWT claims and does not recognize
  `admin.read`. The API's tenant-scoped permission endpoint is working; the
  route-guard correction belongs to the web repository.
- 2026-07-29: The live `Activity.RequestId` column remains `NOT NULL`, so all
  admin workflow writes would fail while creating their required tenant-level
  audit event. The fresh-create SQL was not enough for existing databases.
- 2026-07-29: The earlier unmanaged-model edit made `Comment.requestid`
  nullable instead of `Activity.requestid`. Regression coverage now asserts
  that comments remain request-bound and admin audit activity can be
  tenant-level.
